# 구매자·판매자·관리자 고객 문의 연결

구매자가 남긴 문의를 같은 MySQL에 저장하고, 판매자와 관리자가 자기 상점 문의를 조회합니다. 답변 초안은 내부에만 보이며 관리자의 승인 후 별도 공개 버튼으로 구매자의 문의 내역에 표시합니다.

## 화면별 기능

| 화면 | 기능 | 권한 경계 |
| --- | --- | --- |
| 구매자 `/?support` | 일반 문의·관련 패키지 선택, 문의 접수, 본인 문의·공개 답변 조회 | 로그인된 본인 UID로 서버가 조회. 익명 계정은 간편로그인 후 이용 |
| 판매자 `/#inquiries` | 자기 상점 문의 조회, 기본 안내·AI 초안 생성, 초안 수정·저장, 승인된 답변 공개 | 활성 판매자 역할과 상점 번호를 서버 DB에서 확인 |
| 관리자 `/#inquiries` | 자기 상점의 문의 조회, 유형 수정, 담당 판매자 배정, 상태 관리, 답변 승인·공개 | 활성 관리자 역할 확인. 다른 상점의 계정에 배정 불가 |

기본 분류는 주문·배송 조회, 교환·반품, 주문 변경·취소, 상품·설치, 기타, 복합 문의입니다. 키워드 분류는 추천값이므로 관리자가 수정할 수 있습니다. 비회원·톡체크아웃이라는 구매 경로만으로 반품 문의를 주문조회로 분류하지 않습니다.

최근 30건을 조회하며 이전 문의 더 보기로 추가 조회합니다. 최초 목록만 불러온 상태에서 편집 중이 아니고 화면이 보일 때 15초마다 다시 확인합니다. 이전 페이지를 추가 조회한 경우에는 수동 새로고침합니다. 상태 필터는 불러온 문의에 적용됩니다.

## 데이터 흐름

1. 구매자 Firebase 로그인 토큰을 기존 Vercel 인증 코드가 검증합니다.
2. `/api/inquiries`가 고객 번호를 토큰에서, 상점 번호를 서버의 패키지에서 정합니다. 요청 본문의 고객 번호·상점 번호·상태 주입은 거절합니다.
일반 문의는 단일 상점 구성을 서버에서 확인해 연결합니다. 여러 상점이 존재하면 임의로 선택하지 않고 접수를 거절합니다. 이후 다중 상점으로 확장할 때에는 상점 선택 화면과 서버 검증이 필요합니다.

3. 문의 원문과 상태는 MySQL `inquiries` 한 곳에 저장합니다. 기존 Firestore 주문 접수 구조와 결제 테이블은 변경하지 않습니다.
4. 판매자는 `/api/staff/inquiries`, 관리자는 `/api/admin/inquiries`에서 같은 상점 문의를 읽습니다.
5. 답변 초안은 `inquiries.draft`에 보관하고 구매자 응답에서는 제외합니다.
6. 관리자가 저장된 문구를 검토·승인합니다. 승인 후에도 구매자에게 즉시 보이지 않습니다.
7. 공개 요청은 서버가 행을 잠그고 승인된 문구를 `inquiry_replies`에 복사합니다. 초안·승인을 소진하므로 같은 버전으로 중복 공개할 수 없습니다.
8. 처리 기록은 `inquiry_audit`에 기록합니다. 현재 화면에는 문의별 상세 감사 기록 탐색 기능을 추가하지 않았습니다.

문의 접수와 답변 공개는 실제 결제·취소·환불·배송 또는 카카오·이메일 발송을 실행하지 않습니다. 주문번호 연결, 첨부파일, 구매자의 후속 댓글, 이메일·카카오 알림은 이번 범위에 포함하지 않습니다. 해결·종료 상태와 담당자 배정은 관리자가 관리합니다.

## 승인과 충돌 방지

- 판매자는 초안 작성·저장과 승인된 답변 공개가 가능합니다. 승인과 배정·분류·상태 변경은 관리자만 가능합니다.
- 문의 관리 또는 초안 변경은 서버에서 기존 승인을 해제합니다. 문의 관리 저장은 초안도 비웁니다. 화면에서 이를 안내하고 확인합니다.
- 모든 직원 변경에 `version`을 요구하고 같은 문의 행을 트랜잭션에서 잠급니다. 오래된 화면은 409를 받고 다시 검토해야 합니다.
- 공개는 브라우저가 보낸 문구가 아니라 DB에 저장된 승인 문구를 사용합니다.
- 생성 시 고객별 요청 번호의 고유 키로 같은 요청의 재접수를 구분합니다. 같은 요청 번호에 다른 내용은 거절합니다. 고객별 DB 잠금과 시간당 10건 제한을 적용합니다.
- 현재 재시도 번호는 열린 페이지 메모리에 유지됩니다. 페이지를 닫거나 새로고침한 뒤 다시 접수하기 전에는 내 문의를 확인해야 합니다. 새 요청 번호로 같은 내용까지 자동 중복 판정하지는 않습니다.
- 개인정보·비밀번호·결제정보를 본문에 입력하지 않도록 안내합니다. DB에는 문의 원문이 있으므로 운영자는 보존 기간·삭제 절차·접근 담당자를 별도 정해야 합니다.

## 기본 안내와 실제 AI

기본 안내 초안은 템플릿이며 AI라고 표시하지 않습니다. 페이브릿지는 모의 주문 환경이므로 빅레그의 오전 10시 규칙, 반품 배송비 등 타 쇼핑몰 정책은 사용하지 않습니다.

실제 AI는 서버에서 다음 세 값을 명시적으로 설정했을 때만 호출합니다.

```dotenv
INQUIRY_AI_ENABLED=true
INQUIRY_AI_MODEL=사용할_모델_ID
OPENAI_API_KEY=서버_비밀_환경변수로_설정
```

키를 프론트엔드 공개 환경 변수나 Git 파일에 넣지 않습니다. 모델은 운영자가 계정에서 사용 가능한 ID를 선택합니다. 미설정 시 `AI_NOT_CONFIGURED`를 표시하며 기본 안내·수동 작성은 계속 사용할 수 있습니다.

OpenAI Responses API에 보내는 것은 닫힌 분류값과 고정된 일반 안내 문장뿐입니다. 문의 원문, 구매자 신원, 주문번호, 제목은 보내지 않습니다. `store:false`, 20초 제한, 응답 길이 제한을 설정하고 실행 도구는 제공하지 않습니다. 이 방식은 문장 다듬기에 가깝고 고객별 주문 분석·정책 검색은 수행하지 않습니다. 모델 비용·실제 계정의 호출 가능 여부·생성 품질은 미검증입니다.

공식 구현 근거: [OpenAI 텍스트 생성 안내](https://developers.openai.com/api/docs/guides/text). API 호출은 이번 작업에서 실제로 실행하지 않았고 테스트에서는 가짜 응답을 주입했습니다.

## 반영 순서

1. 테스트용 MySQL에서 `database/006-inquiries.sql`을 적용하고 고객·상점 분리, 중복 요청, 승인·수정·공개를 확인합니다.
2. 운영 DB 관리자가 새 문의 테이블을 적용합니다. 기존 주문·결제 테이블 변경은 없습니다. DB 자격증명을 공개 문서에 붙이지 않습니다.
3. PR을 검토·병합하여 Vercel API·판매자, Firebase 구매자, Cloudflare 관리자 앱을 기존 자동 배포 흐름으로 반영합니다. 자동 배포와 DB SQL 실행은 별개입니다.
4. 관리자 API의 `ADMIN_SITE_ORIGIN`이 실제 관리자 주소와 일치하는지 확인합니다. 기존 인증 서버 환경 변수를 재사용합니다.
5. AI를 사용하려면 별도 서버 환경 변수와 비용 한도를 설정합니다. 기본값은 미활성입니다.
6. 로그인한 구매자 A로 문의 접수 → 판매자 확인·초안 저장 → 관리자 승인 → 판매자 또는 관리자 공개 → 구매자 A 답변 조회를 확인합니다. 구매자 B 및 다른 상점 계정에는 나타나지 않아야 합니다.
7. 승인 직후 초안 수정, 같은 버전 공개 재시도, 오래된 화면 변경도 확인합니다.

운영 DB와 배포된 서비스는 이번 코드 작업에서 수정하지 않았습니다. 병합 전에는 운영 화면에 새 문의 메뉴가 나타나지 않습니다.

## 검증 기록

- 기존 테스트 포함 단위·HTTP·도메인 테스트 101개 통과. 새 문의 테스트 10개 포함.
- 기본 `npm test` 실행기의 임시 소켓 생성이 작업 환경에서 거절되어, 동일한 테스트 파일을 `node --import tsx --test tests/*.test.ts`로 실행했습니다.
- 구매자 Vite, 판매자 Next.js, 관리자 Vite 프로덕션 빌드 통과.
- 세 앱 TypeScript 검사 통과. 실제 실행 환경은 Node.js 24였으며 저장소의 지정 버전은 Node.js 22입니다. CI의 Node.js 22에서도 확인해야 합니다.
- 문의 보안 테스트는 인증·DB 의존성 주입과 모의 DB를 사용합니다. 실제 MySQL SQL 실행·잠금·동시성 검증을 완료한 결과가 아닙니다.
- 실제 계정으로 세 사이트를 연결한 브라우저 시험, 운영 DB 마이그레이션, 실모델 호출, 운영 배포는 미실시입니다.
- 기대 효과의 수치나 시간 절감 실적은 산정하지 않았습니다. 도입 후 접수 누락·응답 시간·초안 수정률을 측정해야 합니다.
